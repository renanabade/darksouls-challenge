# 16. Java 21, and proving the generator did not change

- Status: accepted

## Context

The project moved to Java 21 and Spring Boot from an earlier C# implementation, as the maintainer's work moved to the JVM. Players already
share challenge codes, and a code is a promise: same code, same challenge. A generator that merely looks right would break that in silence.

## Decision

Same results first. The core was ported without changing what it draws, and the reference files written by the earlier implementation stay
as the tests of this one:

- `generator-8-class-hashes.json`: hashes of 200 short manuals, twenty seeds per class.
- `generator-8-manuals.json`: hashes of 67 whole manuals across every length and curve, fixed settings, and groups with handicap.

What could have changed the draw without a compile error, and how it is kept out:

- **No unsigned int in Java.** `sfc32` and FNV-1a wrap the same in `int`, but need logical shifts, and the output needs a mask to `long`.
- **`DoubleStream.sum` compensates its rounding.** A boss's mean defense is summed in a plain loop.
- **`Math.pow` may change once the JIT replaces it.** Keys of the weighted shuffle use `StrictMath.pow`.
- **`String.split` drops trailing empty strings.** Codes are split with a limit of -1.
- **Order of a map.** Everything iterated is a `LinkedHashMap` or sorted first, and sorting is stable, as in the original.

## Consequences

- Changing what the generator draws is still allowed: it takes a version bump and new reference files, on purpose.
- A rule the JVM could have broken is pinned by a file, not by a reader's care.
